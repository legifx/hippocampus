## 0. How to read this

Sections 1–3 are the three goals, each with: what the goal means operationally, what exists,
what was measured today, and the verdict. Section 4 is the list of gaps ranked by what they
cost. Section 5 is what an agent should do next, in order. Every claim of the form "measured"
was produced in this session on the owner's machine with the commands in section 6, so a later
agent can re-run them and diff the numbers against the JSON.

Verdict scale: **met** (built, tested, measured inside budget) · **met with a gap** (true for
what was checked; a named check is missing) · **built, unproven** (code and tests exist; the
criterion needs a human or real use) · **not met**.

## 1. The human: find the right file fast, see everything, verify it is the right one

### 1.1 What the goal means

1. From summoning the window to a painted, correct row: faster than a person can read.
2. Reach a file or a path with what a person already knows — a name fragment, a word, a
   meaning, a place, a time — without learning a new concept first.
3. Overview: a list that stays legible at 400 px and at full width, with the facts that tell
   two similar files apart on the row itself.
4. Verification: a preview of the selected file, so `content.png` and `content(1).png` are
   told apart by looking, not by guessing.

### 1.2 What exists

| capability | where | tested by |

### 1.4 Verdict: **met, with one gap**

Finding a known file is fast by every measure, and the three ways a person reaches one
(name, word, meaning) plus the memory's own places all exist and are keyboard-complete. The
overview holds at every width; the row carries what tells two similar files apart (directory,
size, age, snippet), and the preview pane answers "is this the one" for text, images, PDFs and
video.

**The gap:** there is no test that puts `content.png` and `content(1).png` side by side and
asserts that the row and the preview distinguish them. The pieces exist (directory on the row,
size, age, the thumbnail), and by reading the code they would — but the owner's own example is
not a test, and a thing that is not a test drifts. `brain.diff` exists on the agent surface
and could back a human "compare these two" action; nothing in the window calls it yet.

Two further things about this goal are **built but unproven by a human**: dragging a row out of
the window into another application (the page offers `text/uri-list`; whether WebKitGTK forwards
it to the compositor is unknown), and whether the clipboard survives the window hiding. Both
are thirty-second checks the owner has not yet made (`03-PROGRESS.md` §Start here).

## 2. The agent: the explorer as a brain and a database

### 2.1 What the goal means

An agent working through this system (a) reaches the same files and the same memory a human
does, (b) can write what it learned and get it back at the start of the next session within a
token budget, (c) is measurably better for it, and (d) does all of it under a human's control —
nothing mutates without a plan, everything is audited, a kill switch reaches every tool.

### 2.2 What exists

- **One implementation, three surfaces.** JSON-RPC over the Unix socket, the `cortex` CLI, and
  `cortex-mcp` over stdio expose the same 29 tools; `cortexd/tests/three_surfaces.rs` writes a
  memory through one and reads it back identically through all three against a real daemon.
- **The brain tools** (`docs/07-AGENT-TOOLS.md`): `brain.context` (a context pack inside a
  token budget, MMR-diversified, with a `basis` in words), `brain.remember` / `supersede` /
  `forget_memory`, `brain.outcome` (the learning signal: helped / noise, a human's report
  outweighing an agent's — D76), `brain.search` / `recall` / `explain` / `neighbors` /
  `timeline` / `working_set` / `graph` / `diff` / `annotate` / `link` / `pin`, plus the gated
  filesystem tools `fs.*` and `undo`, and `agent.session.begin/end`.
- **Memory as nodes** (M11, D74–D80): memories live in the same graph as files, with scope
  isolation per surface, supersession with history, salience and tiering, and a second vector
  collection so a recall never competes with 158 000 file chunks (D75).
- **Control:** dry-run plans with ids for every mutation (R6), an append-only audit log
  (`cortex audit`, R8), an undo journal, a persisted kill switch reaching every tool over the
  socket (R7, asserted per tool), deny-list before any content access (R1), and the Agent
  Inspector in the window: sessions and their calls, every memory with provenance and earned
  usefulness, delete/supersede by a human.
- **Reconstructability:** `remember`, `supersede`, `forget_memory` and `outcome` are episodes;
  a rebuild replays a thousand of them, three-deep supersession chains included, to a
  byte-identical dump in 0.55 s (R10, M11 §2).

### 2.3 Measured today

| what | value | budget |
|---|---|---|
| `brain.context`, wall clock from the CLI, real index | 38 ms | 120 ms p95 |
| context pack, 2 048 tokens over 5 000 seeded memories (gate) | p95 10.36 ms | 120 ms |
| memory ANN top-100 in the memory collection | measured in the M11 benchmark, inside 5 ms (recorded 2026-08-24) | 5 ms |
| memories written by any agent on this machine | **0** | — |
| agent sessions ever opened on this daemon | **0** | — |

### 2.4 Verdict: **built and proven; never used in earnest**

Everything the goal names exists and is tested against a real daemon, and the surfaces are
provably the same thing. What is missing is not code: no agent has opened a session on this
machine. M11's twelfth criterion — a real task, twice, through Claude Code, measurably better
the second time — is the one that decides whether the brain is worth its budget, and it can
only be answered by doing it. Until then "the agent side works" means "the tests say so".

One related honesty: the decay curve and the salience weights are tuned for files; whether they
suit a memory is unmeasured, because outcome reports only come from use (D80, the consolidation
report's own `not_done` list).

## 3. Performance: no lag, no big problems

### 3.1 What the goal means

Budgets are the specification (`01-BUILD-PROMPT.md` §Benchmarks): they are CI gates measured on
an idle machine as p95, and a number taken under load does not count — this project has a
recorded case of three sessions optimising something that was never slow.

### 3.2 Measured today

| gate | measured | budget | state |
|---|---|---|---|
| fuzzy path match | 1.19 ms | 10 ms | pass |
| keystroke path, every prefix | 5.88 ms | 10 ms | pass |
| BM25 top-100 | 24.14 ms | 30 ms | pass, the tightest |
| BM25 while the indexer writes | 28.64 ms | 36.21 ms | pass |
| vector ANN top-100 | 1.05 ms | 40 ms | pass |
| RRF fusion + salience | 0.011 ms | 5 ms | pass |
| context pack | 10.36 ms | 120 ms | pass |
| hybrid search, both arms, snippets | p95 45.5 ms | 80 ms keystroke→row | pass |
| daemon idle CPU, 30 s cgroup sample, watcher on 5 780 directories | **0.40 %** of one core | < 0.5 % | pass, close |
| overlay hidden, 30 s cgroup sample | 0.17 % | ~0 | pass |
| overlay visible and idle (D59, 2026-08-21) | 4.8–5.1 % | — | recorded |
| frontend perf suite | 16 of 16 | — | pass |
| **daemon anonymous memory**, embedding model loaded on CUDA | **1 524 MiB** | **250 MiB** | **exceeded** |
| daemon file-backed memory (mapped vector index, page cache) | 255 MiB | reclaimable | as designed (D27) |

### 3.3 The one exceeded budget, explained

The budget was met at 182 MiB anonymous with 100 000 files and no model (D27). Today's daemon
holds 874 MiB in anonymous mappings and 511 MiB of heap beyond that, with the ONNX runtime's
CUDA build loaded and the GPU share capped at 1 024 MiB. The reranker is *not* loaded (its
files are absent; `rerank = true` is therefore inert). The likeliest owner of the difference is
the CUDA runtime's host-side allocations, which no configuration key limits, and this was never
measured with the model resident — every recorded number is from the no-model configuration.

It is not a lag: nothing swaps (the machine has the headroom) and idle CPU is inside budget.
It is a budget that is silently untrue in the configuration the owner actually runs, and the
build prompt says a budget that is not measured is not a budget. **Recommendation:** measure
`RssAnon` with the model loaded on CPU and on CUDA, attribute it (`/proc/<pid>/smaps` by
mapping, or the runtime's own allocator statistics), and then either restate the budget per
configuration or unload the runtime after an idle period — the embedding stage already runs on
a duty cycle (D22) and could release the session when it has nothing to do.

### 3.4 Verdict: **met on every latency and CPU gate; one memory budget exceeded**

No measurement today shows a lag. The three slow calls in a week are one-off 200 ms answers to
status-shaped queries, not the queue that once made scrolling feel slow (D53, `queueing.rs`).
The memory finding is real and new, and is the one number in this review the owner would not
have predicted from the documents.

## 4. Gaps, ranked by what they cost

1. **Daemon anonymous memory 6× its budget with the CUDA runtime loaded** (§3.3). Not a lag
   today; a false claim in the specification. Measure, attribute, decide.
2. **The agent brain has never been used on this machine** (§2.4). Every M11 criterion that
   needs use is open: §12 (a real task twice), §10 (Inspector CPU while streaming), and the
   memory-tuned decay. The cost is that the most novel half of the project is validated only
   by its own tests.
3. **No same-name disambiguation test** (§1.4). Cheap to add; the owner's own example.
4. **Drag-out and clipboard-after-hide unverified** (§1.4). Two manual checks.
5. **M6 §3, the week of exclusive use**, has not been recorded. The file manager's basics are
   all built; whether they are *enough* is a week, not a feature.
6. **The Inspector's layout** was called "im Allgemeinen nicht übersichtlich" by the owner on
   2026-08-24 and deliberately deferred (appearance after stability). It remains the one part of
   the human surface the owner has said is not clear.
7. **The 3D view under WebKitGTK software GL**: the panel now says whether it draws frames; the
   owner has not yet reported whether a picture appears.
8. **The second brain has no bridge yet.** M7 shipped the protocol and both transports; the
   plugin that talks to the real peer belongs to the private Extension and is unwritten.
9. **M9 §1 and D13**: a second person's timed install, and the license file.

## 6. How the numbers were produced

```sh
cortex status; cortex extract; cortex model; cortex memories --json; cortex sessions
cortex search "<q>" --json | jq .elapsed_ms                # internal search time
cortex --as reviewer context "<task>" --json               # a context pack, timed by the shell
cg=$(systemctl --user show -p ControlGroup --value hippocampus-cortexd.service)
a=$(awk '/usage_usec/{print $2}' /sys/fs/cgroup$cg/cpu.stat); sleep 30
b=$(awk '/usage_usec/{print $2}' /sys/fs/cgroup$cg/cpu.stat)
awk -v a=$a -v b=$b 'BEGIN{printf "%.2f%% of one core\n",(b-a)/1e6/30*100}'   # same for the overlay unit
grep -E "RssAnon|RssFile|VmRSS" /proc/$(pgrep -x cortexd)/status
awk '/^[0-9a-f]+-/{n=$6;if(n=="")n="[anon]"} /^Anonymous:/{a[n]+=$2} END{for(n in a)printf "%d MB %s\n",a[n]/1024,n}' /proc/$(pgrep -x cortexd)/smaps | sort -rn | head
journalctl --user -u hippocampus-overlay --since "-7d" -o cat | sed -E 's/\x1b\[[0-9;]*m//g' | grep -E "slow call|slow preview"
cargo run --release -q -p bench-latency                    # the daemon gates, idle machine
cargo test --workspace                                     # 1054
cd ui && npm test && npm run test:ui && npm run test:perf  # 60, 159, 16
```

Code size for scale: about 72 000 lines of Rust across fourteen crates and 14 000 of
TypeScript across the window and the Agent View; 112 commits between 2026-08-17 and today.
